# Frontend API Response and Error Handling

This guide is for frontend developers consuming the ticketing platform APIs. The frontend uses **Axios** for HTTP requests.

## Base Configuration

Use one Axios instance so authentication and errors are handled consistently.

```js
import axios from "axios";

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL || "http://localhost:8080/api",
  headers: {
    "Content-Type": "application/json",
  },
});
```

The backend expects JWT authentication for protected endpoints:

```http
Authorization: Bearer <access-token>
```

## Standard Error Response

Exceptions handled by the backend use this JSON shape:

```json
{
  "timestamp": "2026-07-18T05:41:10.532",
  "status": 404,
  "error": "Resource Not Found",
  "message": "Ticket not found with id: 123",
  "path": "/api/tickets/123"
}
```

| Field | Type | Description |
| --- | --- | --- |
| `timestamp` | string | Server timestamp in ISO date-time format. |
| `status` | number | HTTP status code. |
| `error` | string | Short error category. |
| `message` | string | Detailed error message. |
| `path` | string | Failed API path. |

Axios rejects non-2xx responses. Read the backend error from `error.response.data`, not from `error.message`:

```js
try {
  await api.get("/tickets/123");
} catch (error) {
  const payload = error.response?.data;
  console.log(payload?.status, payload?.error, payload?.message, payload?.path);
}
```

Some failures can be generated by a proxy, browser, network, or Spring Security filter before the controller advice runs. Therefore, always support responses that are empty, HTML, or not in the standard shape.

## Axios Interceptors

### Request interceptor

Attach the current access token to every protected request.

```js
api.interceptors.request.use((config) => {
  const token = localStorage.getItem("accessToken");

  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  return config;
});
```

### Response interceptor

Use one normalizer for backend, network, timeout, and unknown errors.

```js
function normalizeApiError(error) {
  const response = error.response;
  const body = response?.data;

  return {
    status: body?.status || response?.status || null,
    code: body?.error || "Network Error",
    message: body?.message || error.message || "Request failed",
    path: body?.path || error.config?.url || null,
    timestamp: body?.timestamp || null,
    isNetworkError: !response,
  };
}

api.interceptors.response.use(
  (response) => response,
  (error) => {
    const normalized = normalizeApiError(error);

    if (normalized.status === 401) {
      localStorage.removeItem("accessToken");
      // Dispatch an application event or use the router here.
      window.dispatchEvent(new CustomEvent("auth:expired"));
    }

    return Promise.reject(normalized);
  }
);
```

Do not redirect on `403`; the user is authenticated but does not have permission. Do not retry requests automatically from this interceptor unless the request is known to be safe and idempotent.

## HTTP Status Handling

| Status | Backend meaning | Frontend behavior |
| --- | --- | --- |
| `400` | Invalid argument, malformed JSON, missing parameter, type mismatch, validation failure | Show form or field feedback; do not retry unchanged input. |
| `401` | Missing, invalid, or expired authentication | Clear the session and redirect to login. |
| `403` | Authenticated user is not authorized | Show a permission message; remain on the current page. |
| `404` | Resource does not exist | Show a not-found state or refresh the relevant list. |
| `405` | HTTP method is not supported | Treat as a frontend integration/configuration error. |
| `409` | Database uniqueness or integrity conflict | Explain that the data already exists or conflicts with another record. |
| `413` | Uploaded file is too large | Ask the user to select a smaller file. |
| `500` | Unexpected backend error | Show a generic error and allow manual retry. |
| `502`, `503`, `504` | Gateway or service availability error | Show a temporary-service message and offer retry. |

## Global Handler Coverage

`GlobalExceptionHandler` returns the standard shape for:

- `EntityNotFoundException` -> `404 Resource Not Found`.
- `MethodArgumentNotValidException` -> `400 Validation Failed`.
- `IllegalArgumentException` -> `400 Invalid Argument`.
- `HttpMessageNotReadableException` -> `400 Bad Request`.
- Missing parameters, missing path variables, missing multipart parts, and type mismatches -> `400 Bad Request`.
- `ConstraintViolationException` -> `400 Bad Request`.
- `AuthenticationException` -> `401 Unauthorized`.
- `AccessDeniedException` -> `403 Forbidden`.
- `DataIntegrityViolationException` -> `409 Conflict`.
- `MaxUploadSizeExceededException` -> `413 Payload Too Large`.
- `HttpRequestMethodNotSupportedException` -> `405 Method Not Allowed`.
- Any uncaught application exception -> `500 Internal Server Error`.

The backend logs the request method, path, category, message, and complete stack trace in the server terminal. Frontends must not display stack traces or SQL details to users.

## Form Validation

Validation errors currently serialize field messages into the `message` string:

```json
{
  "status": 400,
  "error": "Validation Failed",
  "message": "{title=must not be blank, description=must not be blank}",
  "path": "/api/tickets"
}
```

Treat `message` as text. Do not assume it is an object. If the UI needs field-level errors, validate the same required fields client-side and use the backend message as a fallback.

## Safe Request Wrapper

Use a small wrapper when a component needs consistent success/error behavior:

```js
export async function requestWithUiError(request, { onError } = {}) {
  try {
    const response = await request();
    return response.data;
  } catch (error) {
    const status = error.status;

    if (status === 400) onError?.(error.message || "Please check the form.");
    else if (status === 401) onError?.("Your session has expired.");
    else if (status === 403) onError?.("You do not have permission for this action.");
    else if (status === 404) onError?.("The requested resource was not found.");
    else if (status === 409) onError?.("This data conflicts with an existing record.");
    else if (status === 413) onError?.("The selected file is too large.");
    else if (error.isNetworkError) onError?.("Unable to reach the server.");
    else onError?.("Something went wrong. Please try again.");

    throw error;
  }
}
```

## Retry and Display Rules

- Disable submit controls while a mutation is pending.
- Preserve form input after failed requests.
- Retry only temporary network or `502`/`503`/`504` failures, preferably with a limit and backoff.
- Do not retry `400`, `401`, `403`, `404`, `405`, `409`, or `413` without changing the request or user state.
- Use localized frontend text for normal UI messages; backend `message` is a diagnostic fallback.
- Never display stack traces, SQL, exception class names, or raw server logs.
- Log `status`, `code`, `path`, and a request identifier if a gateway provides one.
- For `204`, do not attempt to parse a response body.
