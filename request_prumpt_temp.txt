You are a full-permission API automation agent and a senior Spring Boot / Java / JPA / PostgreSQL engineer specializing in RBAC and permission-based authorization.

Repository:
https://github.com/yazdan-centos/ticketing-platform.git

Objective:
Implement a robust authorization model for Tickets, Tasks, and Meetings with the following rules:

1. Roles control DATA SCOPE (visibility):
   - Scope is primarily based on Team and Project.
   - Users should only be able to see entities that fall within their allowed scope.

2. Permissions control ACTIONS:
   - CRUD permissions must determine whether a user can create, read, update, or delete Tickets, Tasks, and Meetings.

Current domain assumptions based on the existing codebase:
- Main roles:
  - CUSTOMER
  - TEAM_MEMBER
  - TEAM_MANAGER
- TEAM_MANAGER currently acts as an elevated/admin-like role and may retain broad access.
- Authentication is JWT-based.
- Security is stateless.
- User principal is loaded through UserDetailsService and populated by JwtAuthenticationFilter.
- Meetings belong to Team.
- Tasks belong to Meeting, and therefore indirectly belong to Team.
- Team and Project are the main visibility boundaries.
- You may inspect and refine these assumptions against the actual code before applying changes.

Authorization goals:
- CUSTOMER:
  - Can access only their own tickets and related allowed data, if applicable.
  - Cannot access internal team-wide management data unless explicitly permitted.
- TEAM_MEMBER:
  - Can access tickets, meetings, and tasks within their Team/Project scope.
  - CRUD abilities must be controlled by explicit permissions, not by role name alone.
- TEAM_MANAGER:
  - Has broad access across team-managed resources.
  - May also have admin-level access where already intended by the existing system.
  - Still enforce permissions cleanly rather than relying only on hardcoded role checks.

1. Inspect the existing security, entity relationships, repositories, services, and controllers.
2. Design and implement a clean RBAC + permissions model aligned with the current domain.
3. Use roles for visibility scope and permissions for CRUD authorization.
4. Prevent IDOR vulnerabilities:
   - A user must never access Tickets, Tasks, or Meetings outside their allowed Team/Project/ownership scope, even if they know the ID.
5. You may modify:
   - JPA entity relationships

  - MEETING_CREATE, MEETING_READ, MEETING_UPDATE, MEETING_DELETE
